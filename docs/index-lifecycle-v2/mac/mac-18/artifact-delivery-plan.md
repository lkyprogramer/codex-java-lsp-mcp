# MAC-18 构建、验收和安装拆分方案

当前 `install-runtime.sh` 先构建 release，再从源 checkout 调用完整测试。测试 broker 在另一个目录重新构建。实测同一次安装生成两个不同的 native SHA。安装须等两次构建与完整测试通过，才执行 Gradle 准备和激活。[安装入口](../../../../install-runtime.sh#L351) · [验证入口](../../../../scripts/run-isolated-validation.mjs#L289)

## 目标流程

| 阶段 | 输入和动作 | 通过证据 |
| --- | --- | --- |
| 构建 | 从干净源码冻结 runtime、锁文件和工具链。执行一次依赖安装、加载检查、编译及签名。产出只读 release 和 SHA256 清单。 | 记录源码、runtime、依赖、dist、native 和签名身份。清单区分文件、模式和相对链接。 |
| 验收 | 验证已构建 release 的清单。测试夹具使用独立可写目录。完整测试、受影响 G14 和适用的隔离 canary 对同一工件记账。 | 将命令结果和资源退出证明绑定到 release SHA、native SHA 和 runtime manifest SHA。工件变更时重新判定受影响证据。 |
| 安装 | 只接收通过验收的封存工件。校验包、清单、签名和目标路径。执行目标环境的 Gradle 准备、LaunchAgent 激活和真实读回。 | 运行实例与签名工件一致。失败停止新服务并保留证据。生产固定 launcher 的 TCC 和业务读回需单独授权。 |

## 实施边界

1. 保留现有构建和签名代码。先让验证 broker 接收并核验这个只读 release。测试需要的 Git、夹具和日志放在独立目录。只在 runtime 字节及依赖身份一致时复用验证。完整测试仍是发包前的必过门。
2. 增加从封存工件安装的明确入口。对包 SHA、文件清单、native 签名或验收记录不匹配的情况，在写入安装状态前拒绝。复用现有稳定 launcher、私有 Gradle home 和失败停用逻辑。
3. 用一次隔离交付验证证明安装使用的字节与验收工件一致。读回服务实例、Gradle 准备和真实语义。保留现有恢复与退出断言。通过后再形成具体工件的生产授权请求。

本文件只记录方案。当前安装入口和正式门状态按原记录判定。
