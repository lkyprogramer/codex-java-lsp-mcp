# MAC-12：facts 验证继承的待批准方案

**状态：已被方案B取代（2026-10-22 用户决定，见 [README](README.md#方案b发布前增量检查全库校验放后台2026-10-22按用户要求)），不再实施。下文保留原始核对内容。**

当前保留的四 worker 候选完整 seal 约 4.4–4.6 秒；严格 JSON 试验仍为 4.055–4.143 秒，三组收益均不足 20%，已撤回。其任务线显示完整性、引用检查、facts 解码和 hash 共同构成成本，尚无继续调 worker 数量或顺序能通过编辑可见 3 秒的证据。这些实测不是理论性能下限。

`factsMoved` 不是可复用的证明。它只记录部分解析闭包，创建前已有 `writeBundle`；XML、删除和 full 还有其他写路径。当前 `BuildJob` 和 seal 也没有基线验证来源。不能据此跳过 facts 检查。

建议先批准以下受限的验证合同调整，再做最小实现及成本验证：

1. 完整 schema 的 SQLite full integrity、global quick、FK、census、引用和标量检查仍逐发布执行。原子发布、旧绑定保护、真实退出和全部绝对性能门不变。
2. Full 构建及没有可信基线的候选仍解压并解析全部 facts。仅对持有真实 lease、格式及验证版本受支持、数据库 SHA 已核实且读取期间未改变的基线考虑继承。验证来源必须由本次全量验证成功，或来自可信基线的完整继承证明成功建立；旧快照、缺少来源或来源不明的快照须完整验证，不能只补版本使其成为可信基线。继承证明绑定实际基线 snapshotId、数据库 SHA 和验证版本。
3. Delta 对每条候选 facts 与该基线对应行做 **BLOB 字节相等比较**。仅相等的值继承既有可解码结论；新增或不同的值执行原 `decodeFacts` 的完整解码语义，包括 BLOB 类型、deflate、原 UTF-8 替换语义和 JSON 解析。不信任 builder 提供的变化文件集合。
4. 基线 lease 覆盖所有比较 worker 的实际退出；基线和候选均保持只读及文件稳定性检查。不能证明来源时执行完整验证。确切的验证版本与封存格式变更须在实现前评审，不把旧格式静默视为新合同。
5. 复用现有队列和连接，不增加持久缓存、写日志、worker 池或 codec。修改边界限于 clone/base 生命周期、seal 输入及 facts 校验。若必须超出此边界，再停止评估。

先证明损坏基线、变化 facts、行增删、身份错配、取消和基线失效均不能绕过发布保护；再用同输入三组真实完整 seal 比较，计入新增基线 SHA、比较、lease 和退出成本。每组收益不足 20% 就撤回该试验，不重复挑样本。诊断成功也不能替代全部适用的 G12 full/seed/edit/fairness/physical/query 门及独立复验。

这改变跨 builder/clone/seal 的验证合同，属于局部调参之外的范围，需要用户决定是否投入。收益尚未证明；即使 facts 解码下降，也不能保证完整封存或编辑可见达到 3 秒。
